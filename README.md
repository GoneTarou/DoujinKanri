# 同人制作プランナー

## 1. サービス概要

- どんなサービスか

  - 同人イベントへのサークル参加を目指す個人制作者向けの、制作進捗・締切管理アプリです。作品の総量、締切、作業可能時間から日次目標を自動で作り、工程表で進捗を記録できます。締切直前に作業不足へ気付く状況を減らし、日々の制作を計画的に進められるようにします。

- 誰の、どんな課題を、どう解決するか

  - 同人イベントへのサークル参加を目指す個人制作者が、締切までに必要な作業量を把握できず計画を立てられない課題を、締切・総量・作業可能時間から日次目標を自動計算し、工程表で進捗を記録できる仕組みで解決します。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

- 友人は締切までに必要な作業量や進捗を特に管理しておらず、間に合わないと分かったときには、挽回が難しい状態になっていた。
- 普段から真面目に進めていればよいと考えるかもしれないが、根性論だけで解決しようとするのは再現性のない方法だと思い、進捗管理が良い改善方法になると考えた。

---

### 2-2. なぜそれが「気になった」のか

- 締切までの日数と制作に使える時間をもとに、必要な作業量を日ごとの行動へ落とし込めれば、締切前に慌てて間に合わせる状況を減らせると考えた。
- 締切に間に合わせることができないのは、間に合わせるための仕組みがないからだと考えた。

---

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

- いつまでに何を進めるか決めていないため、制作が締切に間に合わない可能性があること。

---

### 3-2. 本当に解決したい課題は何か

#### なぜそれが困るのか？

- 締切までの日数と、作業に使える時間を結びつけられないから。

  - 作業に使える時間を結びつけられないと、今日どのくらい描くべきか分からず、必要な作業量を下回る可能性があるから。

  - そうしたことが積み重なると、無理なスケジュールでギリギリになってしまったり、締切に間に合わなくなってしまう。

- 本当に解決したい課題：個人制作者が根性論に頼らず締切までの必要作業量を把握し、日々の制作へ落とし込めるようにすること。

## 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)

- サービスを知る・思い出すきっかけ

イベント参加を決め、締切に間に合うか進捗を管理したい時に利用のきっかけになる。作品の総量・締切・作業可能時間を入力すると、日次目標が自動で作成され、日々、制作前に目標を確認し、制作後に工程表へ進捗を記録する。

- 利用のイメージ
  - 漫画は表紙を含む総ページ数を総量として入力
  - 表紙と本文の各ページに、ネーム・下書き・ペン入れ・仕上げなどの工程を記録し、そのページの- 全工程が完了すると完成ページ数が1増える。
  - 完成量の目安と工程表を見て、ユーザー自身が今日の作業を決める必要がある
  - 下書きなど、特定の工程をだけを進めた場合、完成ページは増えないが工程表のページごとの下書き欄に自分でチェックをつける
  - 次回の作業は工程表を確認して次に取り組む工程を選ぶ 日次目標は締切までの完成ペースを判断する材料として利用する あくまで締切までに必要な完成量を配分した目安であり、締切までに必要な完成ページ数・完成枚数を、作業可能時間に応じて日ごとへ割り振ったもの
  - 小説は総ページ数を総量として入力
  - 各ページにプロット・本文・推敲・最終確認などの工程を記録し、全工程が完了したページを完成ページとして数える。
  - イラストは完成させるイラストの総枚数を総量として入力
  - 各イラストにラフ・下書き・線画・色塗り・仕上げなどの工程を記録し、全工程が完了した時点で完成枚数が1増える
  - 総量、開始日、作品締切、イベントを設定
  - 制作前に作品一覧または作品詳細で「今日の目標」を確認できる
  - 締切までの残り完成ページ数・完成枚数を、開始日から締切までの作業可能時間に応じて配分した、その日に必要な完成量の目安
  - 制作後に工程チェック表で、各ページ・各枚について、「ネーム」「下書き」など制作工程ごとに完了した項目へチェックを付ける
  - 工程チェックの記録により、全工程が完了したページ・枚は完成数に加算され、残り完成量が減る
  - 逆に、完成済みの制作対象でチェックを外した場合は完成数が減り、残り完成量が増える。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

- 同人手帳
  - [URL](https://qovo.jp/dojin-techo)
  - どんなことができるか：Webブラウザで同人誌の進捗管理ができる。簡単入力かつふんわりしていても後から調整ができること、登録不要なこと、Twitterでログインをすればバックアップを取ってくれる。

- 原稿プランナー
  - [URL](https://play.google.com/store/apps/details?id=com.takasaworks.genkoplanner&hl=ja)
  - どんなことができるか：有料のスマホアプリで同人誌の進捗管理ができる。スケジュールの自動生成、進捗管理のためのペース診断など、有料なので機能が豊富。

---

### 5-2. それでも自分が作りたい理由

既存サービスである「同人手帳」や「原稿プランナー」のスケジュール作成画面では、より詳細なスケジュールを作成するために、工程ごとの所要時間や自分の制作速度を見積もって入力する。これは、各工程にどれだけ時間がかかるかを把握していない制作者にとって、計画作成を始める際の負担になり得る。

そのため、作業可能時間の曜日別テンプレートを利用して少ない入力で日次の完成目安と工程ごとの進捗を確認できる仕組みを作りたいと思った。

### 5-3. 差別化を「体験価値」で表現する

同人イベント参加を決めた個人制作者が、表を自作せずに締切までの必要作業量を把握し、その日の制作へすぐ取りかかれるアプリ。初めて計画を作る際に、自身の制作速度を見積もれない人でも、計画のたたき台を作ることができるので、利用ユーザーの負担を減らすことができるアプリ。

- 差別化ポイントを一言で表すと
  - 締切までの作業量を、少ない入力量で計画を作成することが可能で、日々の制作目標へ自動で変えること。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

このサービスを使うことで、ユーザーはどう変化しますか？

- 行動の変化：日々必要なページ数を確認し、工程表へ進捗を記録する。
- 気持ちの変化：締切直前に漠然と焦るのではなく、必要な作業量を把握して制作に取り組める。
- 考え方の変化：締切管理を根性論ではなく、計画と進捗確認で進められるようになる。

### 6-2. 価値を一文で表す

同人イベント参加を目指す個人制作者が、締切までの必要作業量を把握して日々の制作を進められるようになるサービス。

## 8. このアプリの懸念点とその対策

### 懸念点①

- 何が問題になりそうか：ユーザーが進捗を記録し続けられない可能性がある。
- なぜそう思うか：日々の制作で忙しいと、管理そのものが負担になり、使われなくなる可能性がある。
- そのために考えている対策：作品登録時に工程表を自動作成し、制作後はチェックするだけで進捗を反映できるようにする。

## 9. 今後の展開・発展の方向性

### 観点（すべて答えなくてOK）

- ユーザーはなぜ使い続ける？

  - イベントごとに新しい作品と締切が生まれるため、その都度、必要な作業量を確認する必要がある。日次目標の確認と工程表への進捗記録を、制作を始める前後の習慣として使い続けてもらう。

- 続けることで何が変わる？

  - 締切直前に進捗不足へ気付くのではなく、早い段階で必要な作業量を把握し、計画的に制作を進められるようになります。

- データが溜まると何ができる？

  - 将来的には、過去の作品にかかった期間や工程ごとの進み方を振り返り、次の作品の締切や総量を設定するときの参考にできます。

- 他の人と関わる余地はある？

  - 将来的には、同じイベントに参加する友人と作品の進捗を共有したり、互いに制作予定を確認したりする機能を検討できます。ただし、MVPでは個人で無理なく管理できることを優先します。

- 運用・仕組みで価値を出せないか？

  - イベント参加を決めた直後に計画作成を促し、締切・総量・作業可能時間を入力するだけで日次目標を作れる導線を整えます。表を自作したり計算したりしなくても、すぐ制作に取りかかれる体験を提供します。

### 今考えている発展案

- 機能追加の方向性：データ出力の追加
- UI・体験の改善：スマホ・タブレット対応
- 機能以外の工夫：イベント参加を決めた直後に使い始めやすい導線を設計する

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- フレームワーク：Rails（HotWire）
- DB：開発環境はSQLite、本番環境はPostgreSQL
- デプロイ先：Render
- 使用予定ライブラリ：Devise、Tailwind CSS、DaisyUI
- テスト：Minitest

---

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Rails + HotWire | 採用 | 画面・認証・データ処理を一つのアプリで実装できるため |
| React | 不採用 | MVPではフロントエンドとバックエンドを分離しないため |
| SQLite | 採用 | 開発環境でのみ使用 本番環境ではPostgreSQLで永続データを運用 |
| PostgreSQL | 採用 | RailsとRenderの構成に適しているため |
| Render/Neon | 採用 | どちらも無料枠があり初期コストを抑えられるため |
| Heroku | 不採用 | 無料プランが廃止されているため |

- 今回チャレンジしたい点

  - local Storage機能を用いたゲストユーザーでも操作ができる機能を実装
  - Deviseによる認証機能の実装

- 不安な点

  - local Storage機能によるゲストユーザー作成は理解が曖昧なため、実装時にキャッチアップが必要
  - 今までのアプリ制作では、Rails標準の認証機能でしか実装していなかったため、Deviseによる認証機能の実装はキャッチアップが必要

---

### 10-3.キャッチアップ不足の懸念

1. local Storageの理解が浅く、それ自体のCookieとの違いを十分に理解していない。

どのような仕組みかを整理し、今回の機能実装にはどういった設計で取り入れるかを考える必要がある。
2. Issueの見積もりが難しい

調査範囲が曖昧であり、理解できている部分と理解不足な部分の境界も不明瞭。Issueごとに作業時間を適切に予測することが難しい。
3. 設計と実装が最適かどうかの判断が難しい

保守しやすい設計・実装の判断やキャッチアップに時間を書ける必要な可能性がある。
